# DTB delivery on Snapdragon X: live ISO (GRUB) and installed system (Limine)

Research for JimmayVV/omarchy-iso#3 (map: #1). Written 2026-08-24 against: Arch Linux ARM
`linux-aarch64` 7.2-2, `systemd` 261.2, `limine` 12.6.0, `grub` 2.14, archiso at the pinned
submodule commit `424e7813`, dtbloader 1.5.4, upstream PR omacom-io/omarchy-iso#121 as of today.

## TL;DR

Snapdragon X laptops boot with ACPI-only firmware and no device tree in the UEFI configuration
table. Something in the boot chain has to identify the machine and publish the right
`qcom/<board>.dtb` as the `EFI_DTB_TABLE_GUID` configuration table before the kernel's EFI stub
runs. Every serious option does exactly that; they differ only in *what* does the matching and
*where* the DTBs live.

**Recommendation: one mechanism for both live and installed — a systemd-stub UKI carrying every
Snapdragon X DTB in `.dtbauto` sections plus systemd's shipped CHID database in `.hwids`.**

- The stub computes SMBIOS CHIDs at boot, finds the matching `compatible` in `.hwids`, picks that
  `.dtbauto` section, installs it as the DTB config table, and boots the embedded kernel.
  systemd 257 added the sections; systemd 260 ships the device database at
  `/usr/lib/systemd/boot/hwids/aa64/` (39 Snapdragon JSON files, **including
  `x1e80100-hp-elitebook-ultra-g1q.json`**, imported 2026-02-02). ALARM has systemd 261.2 and
  `systemd-ukify`.
- Installed: Omarchy already boots a UKI (`/boot/EFI/Linux/omarchy_linux.efi`, built by
  `mkinitcpio --uki` through limine-entry-tool, chainloaded by Limine's `efi` protocol). mkinitcpio
  uses `ukify` when it is installed and passes `/etc/kernel/uki.conf`. So the whole change is: install
  `systemd-ukify`, and write a `uki.conf` with `DeviceTreeAuto=` listing the kernel package's
  `/boot/dtbs/qcom/x1*.dtb glymur*.dtb`. Limine is untouched.
- Live: build the same kind of UKI in `customize_airootfs.sh` (kernel + archiso initramfs + fixed
  cmdline + `.dtbauto`/`.hwids`) and have GRUB `chainloader` it. GRUB's `linux` command validates the
  arm64 Image header and Fedora needed a GRUB patch for stub-wrapped kernels; `chainloader` needs
  neither. One extra archiso patch (copy `/boot/*.efi` into the ISO tree) on top of the module-list
  patch #121 already needs.
- Model-agnostic: nothing in the ISO or installer names the G1q. Supporting a new X1 or X2 laptop is
  "its DTB exists in `linux-aarch64` and its hwids JSON exists in systemd" — both upstream
  contributions, both generated by scripts (`fwupdtool hwids` / dtbloader's `describe_hw.sh`).
  Local override: drop extra JSON in a directory and point `HWIDs=` at it.

dtbloader stays the documented fallback for a device that needs *runtime DT fixups* (Wi-Fi/BT MAC
provisioning on some Lenovo/Dell boards). The G1q entry in dtbloader has no fixup callback, so it
does not need one.

## The problem, precisely

- Windows-on-ARM firmware boots with ACPI. Linux on x1e80100 does not run from those tables; the
  kernel needs a flattened device tree. Firmware provides none, so `EFI_DTB_TABLE_GUID` is absent from
  the configuration table and the kernel's EFI stub (`drivers/firmware/efi/libstub/fdt.c`,
  `get_efi_config_table(DEVICE_TREE_GUID)`) finds nothing.
- The kernel's own `dtb=` cmdline loader needs `CONFIG_EFI_ARMSTUB_DTB_LOADER`, which ALARM's
  `linux-aarch64` config does **not** set, and it is ignored under Secure Boot anyway.
- ALARM's `linux-aarch64` PKGBUILD runs `make dtbs_install` into `/boot/dtbs/`, so the installed
  package provides `/boot/dtbs/qcom/x1e80100-hp-elitebook-ultra-g1q.dtb` (mainline since v6.17) and
  every other X1 board the kernel knows. Kernel 7.2 ships 25 `x1e*/x1p*` boards and `glymur-crd`
  (the Snapdragon X2 Elite reference design, since v7.1). No X2 retail laptop DTS is upstream yet.
- The G1q DTS's first compatible is `hp,elitebook-ultra-g1q` (then `qcom,x1e80100`). Every
  mechanism below matches on either that string or on SMBIOS-derived CHIDs.

Secure Boot must be off on the G1q for any of this (archiso's GRUB is unsigned, dtbloader is
unsigned, and GRUB's `devicetree` is disabled under lockdown). That is already the Ubuntu and
dtbloader position; not a differentiator between options.

## Mechanisms evaluated

### 1. TravMurav/dtbloader (EFI driver)

Source read: `src/main.c`, `src/util.c`, `src/include/device.h`, `src/devices/hp_elitebook_ultra_g1q.c`,
`Makefile`, README, releases, issue #8.

- A UEFI **driver** (`-subsystem:efi_boot_service_driver`), not an application. `efi_main` runs
  `match_device()` (SMBIOS type 1/2 → CHID GUIDs compared against a compiled-in table, one C file
  per device, 35 devices), opens the volume it was loaded from
  (`LoadedImage->DeviceHandle` → `SimpleFileSystem`), looks for the device's DTB name under
  `\dtbloader\dtbs\`, `\dtbs\`, `\` (also with the `qcom\` prefix stripped), applies the device's
  optional `dt_fixup` callback, and `InstallConfigurationTable(EFI_DTB_TABLE_GUID, dtb)`. It also
  installs `EFI_DT_FIXUP_PROTOCOL` so a loader that brings its own DTB (sd-stub, sd-boot) can still
  get the fixups. Then it returns `EFI_SUCCESS` and stays resident.
- The G1q entry: 15 CHIDs, `.dtb = L"qcom\\x1e80100-hp-elitebook-ultra-g1q.dtb"`, **no fixup**.
- Under Secure Boot it stores a SHA-1 of the DTB in an NV variable and prompts when it changes.
- Ways to get it executed, per README: (a) sd-boot's driver directory
  `/EFI/systemd/drivers/dtbloaderaa64.efi`; (b) firmware `DriverOrder` via
  `efibootmgr -r -c -l dtbloader.efi`; (c) `bcfg driver add` from the EFI shell, "on some devices
  you may need to add optional data to the driver entry for firmware to load it".
- Not in the source: any chainloading, any "panel overlay", any `UEFIDisplayInfo` (code and issue
  search return zero hits). Display variant handling is done with `extra_match` callbacks on
  specific devices (T14s LCD vs OLED), not overlays. The ticket's premise on that point was wrong.
- Releases 1.0 (2024-08) through 1.5.4 (2026-04-05); the asset is `dtbloader.efi` (rename to
  `dtbloaderaa64.efi` for sd-boot). Issue #8 (X1 device coverage) is closed; every listed device was
  merged by 2025-09 including the G1q.
- Not packaged in Arch, ALARM, or AUR. Building needs clang + lld.
- **With GRUB**: GRUB has no driver directory. `chainloader /dtbloader.efi` then `boot` should work
  from source reading — `grub_chainloader_boot` calls `StartImage`, and when the driver returns
  `EFI_SUCCESS` it returns `GRUB_ERR_NONE` and `grub_loader_unset()`, so the menuentry script can
  continue to `linux`/`initrd`, and GRUB's arm64 loader then finds the config-table DTB via
  `grub_efi_get_firmware_fdt()`, adds `linux,initrd-*` to a copy, and installs it. Two catches:
  dtbloader opens the volume it was loaded from through `SimpleFileSystem`, which firmware only
  provides for FAT — so **both the driver and the DTBs must be inside `efiboot.img`**, not the
  ISO9660 tree, and `_make_bootmode_uefi.grub()` never copies profile files into `efiboot.img`
  (needs a mkarchiso patch). And Canonical's stubble spec states dtbloader "is loaded as an EFI
  driver which is currently not compatible with grub" — the chainload trick is untested territory.
- **With Limine**: works transparently if the driver ran *before* Limine (DriverOrder). Limine's
  `get_device_tree_blob()` falls back to the `EFI_DTB_TABLE_GUID` table when neither `dtb_path` nor
  `global_dtb` is set, and its `efi` chainload just calls `LoadImage`/`StartImage`, so a UKI booted
  through Limine sees the table too. Limine itself cannot load drivers.

### 2. GRUB `devicetree` (+ `smbios`)

- `devicetree FILE` loads a DTB through GRUB's own filesystem drivers (ISO9660 is fine) and
  *replaces* the firmware DTB; registered with `grub_register_command_lockdown`, i.e. refused under
  Secure Boot lockdown. Module `fdt` is not in mkarchiso's list; `smbios` and `regexp` — `regexp` is,
  `smbios` is not.
- Selection has to be scripted in `grub.cfg`. GRUB cannot compute CHIDs (no SHA-1 in script), so the
  only handle is product/baseboard strings: `smbios --type 1 --get-string 5 --set product`,
  `regexp`, then `devicetree /arch/boot/aarch64/dtbs/qcom/x.dtb`. That is exactly what the
  Ubuntu concept ISO does (its `grub.cfg` matches `$system_product_name` with `regexp` and sets
  `dtb="devicetree /casper/dtbs/…"`, per the G1q Launchpad bug).
- Zero new binaries, no `efiboot.img` patch, DTBs come straight from the kernel package on the
  ISO. Cost: a product-name table someone maintains, and no DT fixups. It is the cheapest thing
  that could possibly work and a fine emergency fallback, but it is a hand-kept table of laptop
  names, which is what the map's "model-agnostic" requirement is trying to avoid.

### 3. Limine's own DTB options

CONFIG.md (trunk) and `common/lib/misc.c`, `common/protos/linux_risc.c`, `common/protos/chainload.c`:

- `dtb_path` (per entry, `linux` and `limine` protocols) and `global_dtb` (also used by Limine itself)
  — a single static file "instead of the one provided by the firmware". If neither is set, Limine
  reads the firmware config table. There is no matching logic of any kind.
- Limine's `linux` protocol on aarch64 is a direct-entry loader (`linux_risc.c`): it patches
  `/chosen` (bootargs, initrd, UEFI mmap/system table) and jumps to the Image, **bypassing the EFI
  stub**. The CONFIG.md note that this is "of limited use" on aarch64 is why Omarchy's UKI-through-
  `efi`-chainload path is the right one to stay on.
- So Limine alone can only do "installer detects the machine once and writes `dtb_path`". Detecting
  at install time is easy on a live system that already booted with the right DT
  (`/proc/device-tree/compatible` → `fdtget` over `/boot/dtbs/qcom/*.dtb`), but the result is a
  hardcoded path in `limine.conf` on the target, and Omarchy does not use the `linux` protocol
  anyway. Rejected as the primary mechanism; noted as a debugging escape hatch.

### 4. systemd-stub `.dtbauto` + `.hwids` (what Fedora and Ubuntu converged on)

systemd-stub(7), ukify(1), NEWS, `src/boot/hwids/`, `src/boot/meson.build`:

- A UKI may carry zero or more `.dtbauto` sections and one `.hwids` section. "If the firmware does
  not provide a DeviceTree, the match is done using the `.hwids` section": the stub computes CHIDs
  from SMBIOS, finds the entry, takes its `compatible`, loads the `.dtbauto` whose first
  `compatible` matches, installs it, and also honours `EFI_DT_FIXUP_PROTOCOL` if some driver
  installed one. Added in systemd 257.
- systemd 260 ships "a canonical set of hwid files" at `/usr/lib/systemd/boot/hwids/<efi-arch>/`
  (installed by `install_subdir('hwids', install_dir: libexecdir/'boot/')` when ukify is enabled).
  `ukify` auto-populates `.hwids` from that directory when `--hwids` is not given. The aa64 set has
  39 files; the G1q file maps 13 CHIDs to `compatible: hp,elitebook-ultra-g1q`, which is the DTS's
  first compatible.
- `ukify` config keys: `DeviceTreeAuto=` (whitespace-separated list, one section each),
  `HWIDs=` (directory of JSON). mkinitcpio's `uki_init()` runs `ukify build --config=/etc/kernel/uki.conf`
  when `ukify` is on PATH (else it falls back to objcopy with `linuxaa64.efi.stub`, which cannot
  add these sections). Arch/ALARM split ukify into `systemd-ukify`.
- Limit: one PE section per DTB, ~96 sections per image (systemd#35943). 25–30 Snapdragon X DTBs
  at ~150 KB each is well inside that and adds a few MB to the UKI.
- **Fedora 44** ("Automatic DTB selection for aarch64 EFI systems", de Goede/Gompa): ships the
  kernel as `kernel-dtb-loader` = systemd-stub (packaged as **Stubble**) + kernel + `.dtbauto` +
  `.hwids`, *without* initrd or cmdline, so GRUB keeps supplying those. They explicitly rejected
  dtbloader because it uses "a fixed DTB path / fixed builtin DTBs whereas we really want separate
  DTBs per kernel version", would force a switch to systemd-boot, and cannot be signed with the
  distro key. Deliverables include "fix GRUB to properly boot kernel images with systemd-stub".
- **Ubuntu**: the 24.10/25.04 concept ISOs (`*-desktop-arm64+x1e.iso`) select DTBs in `grub.cfg`
  via SMBIOS product-name `regexp` + `devicetree` (mechanism 2). The stubble spec (Canonical)
  makes stubble the default for the arm64 `linux-generic` kernel on Snapdragon X in 25.10 and
  26.04 LTS: `vmlinuz` becomes stub + `.linux` + `.dtbauto`×N + `.hwids`, signed as one PE, booted by
  GRUB + shim. The hwids database ships in `/usr/share/stubble/hwids` and is the same CHID JSON
  format systemd uses (stubble is "compatible with systemd-stub and ukify").
- Both distributions therefore boot *GRUB → stub-wrapped kernel → CHID match → DTB → kernel*, with
  GRUB patched so its `linux` command accepts the PE. We can avoid the GRUB patch by chainloading a
  full UKI instead of `linux`-loading a stub-wrapped kernel.

### 5. Kernel EFI stub `dtb=` — rejected

Not built in ALARM's config (`CONFIG_EFI_ARMSTUB_DTB_LOADER` absent), disabled under Secure Boot,
and it still needs something to choose the file. Listed for completeness.

## How this repo does it today

- `configs/profiledef.sh`: `arch="x86_64"`, `bootmodes=('bios.syslinux' 'uefi.grub')`. No
  `efiboot`/systemd-boot bootmode; `configs/efiboot/loader/entries/01-archiso-x86_64-linux.conf`
  is dead (only `uefi.systemd-boot` reads it — PR #121's own note).
- `configs/grub/grub.cfg`: two menuentries doing `linux /%INSTALL_DIR%/boot/%ARCH%/vmlinuz-linux-t2 …`
  + `initrd …`. GRUB reads kernel and initramfs from the ISO9660 tree; `efiboot.img` holds only
  `BOOT{x64,AA64}.EFI` and the EDK2 shell (`_make_bootmode_uefi.grub()` does not call
  `_make_boot_on_fat`).
- mkarchiso `uefi.grub` on aarch64: `grub-mkstandalone -O arm64-efi` with an x86-derived module
  list (#121 reports `at_keyboard keylayouts usb usbserial_*` are missing for `arm64-efi` and the
  build aborts; #121 leaves that as an archiso patch). The embedded `grub-embed.cfg` searches the
  ISO by UUID/label and loads `/boot/grub/grub.cfg`. The output lands as `/EFI/BOOT/BOOTAA64.EFI`.
- Installer (`phases_impl.py`): `_configure_limine_boot` → `_install_limine_efi` copies
  `/usr/share/limine/BOOTX64.EFI` to `$ESP/EFI/limine/limine_x64.efi` (or `/EFI/BOOT/BOOTX64.EFI` when
  removable), registers it with `efibootmgr`, writes a pacman hook to re-copy on upgrade;
  `validate_boot` checks the binary and `limine.conf`. `context.py` seeds
  `omarchy_install.boot = {esp_mount: /boot, esp_path: /EFI/limine, efi_binary: limine_x64.efi}`.
  The kernel entries themselves come from `limine-mkinitcpio-hook` (Zesko's limine-entry-tool
  1.37.1, `arch=('x86_64' 'aarch64')`), with Omarchy's `etc/limine-entry-tool.d/omarchy-uki.conf`
  setting `ENABLE_UKI=yes` and `CUSTOM_UKI_NAME="omarchy"` → `/boot/EFI/Linux/omarchy_linux.efi`.
  The tool runs `mkinitcpio` to build the UKI and writes an `efi`-chainload entry for it.
- PR #121 diff, as far as it touches boot: `profiledef.sh` selects `arch`/`bootmodes`/compression
  per `uname -m` (aarch64 → `uefi.grub` only, xz+`-Xbcj arm` because ALARM lacks
  `CONFIG_SQUASHFS_ZSTD`); `build-iso.sh` rewrites the kernel name in every `grub/*.cfg`
  (`vmlinuz-linux-t2` → `vmlinuz-linux-aarch64`), stages `configs/aarch64/{zz-aarch64-live.conf,
  linux.preset, customize_airootfs.sh}`; `customize_airootfs.sh` copies `/boot/Image` to
  `/boot/vmlinuz-linux-aarch64`, writes a live preset with `archiso_config=`, and runs
  `mkinitcpio -p linux-aarch64` inside the chroot; `context.py`/`phases_impl.py` derive
  `BOOTAA64.EFI` / `limine_aa64.efi` from `platform.machine()`. **Nothing in #121 touches device
  trees**; it is a generic UEFI aarch64 ISO, which is exactly the layering the map wants.

## Boot chains

### Live ISO — recommended (UKI chainloaded by archiso's GRUB)

```
Firmware (ACPI only, no DTB table)
  └─ removable-media path: efiboot.img:/EFI/BOOT/BOOTAA64.EFI   (grub-mkstandalone arm64-efi)
       └─ embedded grub-embed.cfg: search ISO by UUID → /boot/grub/grub.cfg
            └─ menuentry: chainloader /arch/boot/aarch64/omarchy-live.efi   (from ISO9660)
                 └─ LoadImage/StartImage → systemd-stub (linuxaa64.efi.stub)
                      ├─ no EFI_DTB table → compute CHIDs from SMBIOS
                      ├─ .hwids: CHID ba2ddd3d-… → compatible "hp,elitebook-ultra-g1q"
                      ├─ .dtbauto[k] with matching compatible → InstallConfigurationTable(EFI_DTB)
                      ├─ (EFI_DT_FIXUP_PROTOCOL if any driver installed one — none here)
                      └─ .linux (Image) + .initrd (archiso initramfs) + .cmdline
                           └─ kernel EFI stub: get_efi_config_table(DEVICE_TREE_GUID) → boot
                                └─ archiso hook mounts squashfs by archisolabel=OMARCHY_YYYYMM
```

The `.cmdline` is fixed at build time (`archisobasedir=arch archisolabel=<iso_label> quiet splash
initramfs_async=0 …`); `iso_label` is date-derived in `profiledef.sh` from `SOURCE_DATE_EPOCH`, which
`build-iso.sh` can export so the chroot and mkarchiso agree. Keep the plain `linux`/`initrd`
menuentry too — it will only boot on machines whose firmware supplies a DT, but it costs nothing
and is the x86-identical path.

### Live ISO — alternatives, in case the chainload path misbehaves on the G1q firmware

- **L-alt-1, dtbloader via GRUB `chainloader`**: `chainloader (${archiso_efidev})/dtbloader.efi`,
  `boot`, then the stock `linux`/`initrd` lines. Requires dtbloader + `dtbloader/dtbs/qcom/*.dtb`
  inside `efiboot.img` (mkarchiso patch), `chain` module (present), and the "boot returns to the
  script" behaviour verified.
- **L-alt-2, switch aarch64 to `uefi.systemd-boot`**: dtbloader in `/EFI/systemd/drivers/`, the
  documented path. Needs the same `efiboot.img` patch, and sd-boot can only read its own ESP, so
  kernel + initramfs get duplicated into the FAT image (~+100 MB ISO). Diverges from #121's
  GRUB-everywhere choice.
- **L-alt-3, `smbios` + `devicetree` table in `grub.cfg`**: no binaries, no patches beyond adding
  `fdt smbios` to the module list; hand-maintained product-name table. Ubuntu concept did this.

### Installed system — recommended (unchanged Limine, richer UKI)

```
Firmware (ACPI only)
  └─ Boot#### "Limine" → $ESP/EFI/limine/limine_aa64.efi        (installer, #121 naming)
       └─ limine.conf entry "Omarchy" → protocol: efi, image_path: boot():/EFI/Linux/omarchy_linux.efi
            └─ chainload(): LoadImage/StartImage of the UKI       (limine-entry-tool writes the entry)
                 └─ systemd-stub: no EFI_DTB table → CHIDs → .hwids → .dtbauto → install table
                      └─ .linux + .initrd + .cmdline → kernel EFI stub reads DTB table → boot
```

UKI build path on the target: `limine-mkinitcpio-install` → `mkinitcpio --uki … --ukiconfig` →
`uki_init()` sees `ukify` on PATH → `ukify build --config=/etc/kernel/uki.conf --linux=… --initrd=…`.
`/etc/kernel/uki.conf` carries `[UKI] DeviceTreeAuto=/boot/dtbs/qcom/x1e80100-….dtb …` and (optionally)
`HWIDs=/usr/lib/systemd/boot/hwids/aa64` (the default when the directory exists). Every kernel
upgrade rebuilds the UKI with that kernel's own DTBs — Fedora's "separate DTBs per kernel
version" argument, for free. Snapshots/fallback UKIs get the same sections because they go through
the same builder.

### Installed system — alternatives

- **I-alt-1, dtbloader in firmware `DriverOrder`** + `$ESP/dtbloader/dtbs/qcom/*.dtb` copied by a
  pacman hook on `linux-aarch64` upgrade. Works with any loader, but depends on this firmware
  honouring `Driver####` (README warns some need optional data), lives in NVRAM (wiped by a firmware
  reset, invisible to a reinstall), and needs a binary we build ourselves. Keep as the fallback for a
  device that needs a fixup callback.
- **I-alt-2, Limine `linux` protocol + `dtb_path`** chosen once by the installer. Static path,
  bypasses the EFI stub, contradicts Omarchy's UKI design. Debug-only.

`build-iso.sh` vs installer split: the ISO build owns the live UKI and the extra packages in the
offline mirror; the installer owns nothing new except dropping `uki.conf` on the target before the
first `limine-mkinitcpio` run (the `finalize_limine_boot` phase is the natural place, "after hardware
drop-ins"). No new EFI binaries anywhere in the recommended path.

## Staying model-agnostic for X1 and X2

- Matching is by SMBIOS CHIDs, computed at boot from the machine in front of the stub; nothing is
  keyed on the G1q. The `DeviceTreeAuto=` list is a glob over whatever the kernel package installed
  (`x1e*`, `x1p*`, `glymur*`, plus future X2 board prefixes).
- A new X1 laptop works when (a) its DTS is in the kernel and (b) its hwids JSON is in systemd —
  both scripted (`fwupdtool hwids` / dtbloader `scripts/describe_hw.sh`, then `hwid2json`). Until
  (b) lands upstream, a local JSON in e.g. `/etc/kernel/hwids/` can be merged into the `HWIDs=`
  directory by the build; the format is public and tiny.
- X2 Elite ("Glymur"): kernel has only `glymur-crd` (v7.1+); neither dtbloader nor systemd has a
  retail X2 device yet. The mechanism needs no change — the map's "what must differ for X2" item
  reduces to the two upstream contributions above plus whatever firmware/driver differences the
  kernel work uncovers. Section count (~96) leaves room for the whole X1 + X2 catalogue.
- Compatible-string matching is the same key Fedora, Ubuntu (stubble) and dtbloader all use, so
  device work done for any of them carries over.

## Recommendation and how to verify it

1. Installed first, because it is the smaller change and everything is already in place:
   `systemd-ukify` + `/etc/kernel/uki.conf` with `DeviceTreeAuto=` → rebuild → inspect with
   `ukify inspect /boot/EFI/Linux/omarchy_linux.efi` (expect N `.dtbauto` + `.hwids`).
2. Live: build the UKI in `customize_airootfs.sh` after the initramfs it already produces, add a
   `chainloader` menuentry, patch mkarchiso to copy `/boot/*.efi`.
3. QEMU can test the *selection* without the laptop: `qemu-system-aarch64 -machine virt` with
   AAVMF and `-smbios type=1,manufacturer=HP,product='HP EliteBook Ultra G1q 14 inch Notebook AI PC',family='103C_5336AN HP EliteBook Ultra',sku='A3LZ2AA#ABA' -smbios type=2,manufacturer=HP,product=8CBE`
   (values from dtbloader's `scripts/hwids/x1e80100-hp-elitebook-ultra-g1q.txt`; dtbloader's own
   `scripts/run_qemu.sh` uses the same trick). The kernel will not run on the virt machine with an
   x1e DTB, but `systemd-stub` prints which DTB it picked and `/proc/device-tree/model` can be checked
   from a `virt` DTB variant; the point is exercising CHID → compatible → section on the x86 box.
4. Real hardware: live USB on the G1q with Secure Boot off; check `dmesg | grep -i 'DTB\|device tree'`
   and `/proc/device-tree/compatible` reads `hp,elitebook-ultra-g1q`.
5. Keep dtbloader as documented plan B, and if it is ever needed, prefer I-alt-1 (DriverOrder) on
   the installed system and L-alt-1 on the ISO.
